# RFC：Cocode Nut 统一 $60 套餐额度与模型折算扣费

- 状态：Implemented
- 日期：2026-08-27
- 范围：Cocode Nut 套餐额度、模型定价配置、Host/Harness 扣费链路、GUI 额度展示
- 目标版本：第一阶段只提供 6 个模型

## 1. 摘要

Cocode Nut 用户每月支付 $10，账户页面始终展示一个统一的 $60 套餐额度。用户可以在允许的模型之间切换，但不同模型使用不同的额度扣减系数：AIBerm 折扣越高，模型消耗 $60 的速度越慢；AIBerm 折扣越低，模型消耗 $60 的速度越快。

每个模型同时有一个 **$40 的官方等值用量上限**。这个 $40 是单模型政策上限，不是为每个模型单独开一个 $40 钱包；真实账户仍然只有一个 $60 总余额。用户混用模型时，所有模型共同消耗这一个总余额。

本 RFC 的核心设计是：

1. 账户只保存一个套餐余额 quotaBalanceUsd = 60。
2. 请求费用先沿用 Cocode Nut 已有的官方 API 计价，得到一个 officialCostUsd。
3. 再乘以模型折算系数，得到从 $60 套餐余额中扣除的额度。
4. 单模型的 $40 上限按官方等值费用统计，不新增独立模型余额。
5. 在当前成本假设下，用户把 $60 套餐额度全部用完时，AIBerm 上游成本最多为 $8.40，保留 $0.60 预留后，收入 $10 的目标利润为 $1.00。

## 2. 背景与问题

当前产品需要同时满足四个条件：

- 对外承诺：用户支付 $10，看到 $60 额度。
- 模型差异：gpt-5.6-sol 系列、Claude Fable 5、Claude Opus 5、Claude Sonnet 5 的 AIBerm 折扣不同。
- 共享余额：用户切换模型时，额度不能被每个模型各自复制一份。
- 成本控制：所有模型混合使用后，AIBerm 总成本仍需受套餐预算约束。

如果直接让所有模型都按官方价格 1:1 扣 $60，无折扣或低折扣模型可能产生接近 $60 的上游成本，无法保证利润。如果为每个模型单独设置 $40 余额，又会把多个 $40 叠加成不可控的总承诺。

因此需要将“用户看到的统一额度”和“不同模型的实际消耗速度”分离：用户只看到一个总余额，系统内部按模型折算系数扣费。

## 3. 目标

### 3.1 产品目标

- 用户账户初始显示 $60.00 统一额度。
- 允许用户使用以下 6 个模型：
  - gpt-5.6-sol（兼容别名：gpt-5.6）
  - gpt-5.6-luna
  - gpt-5.6-terra
  - claude-fable-5
  - claude-opus-5
  - claude-sonnet-5
- 每个模型显示并执行 $40.00 官方等值用量上限。
- 用户混用模型时，仍然只有一个总余额。
- 用户可以实时看到当前模型预计还能使用多少官方等值额度。
- 额度扣减结果可解释、可审计、可重放。

### 3.2 经济目标

- $10 收入中预留 $0.60 用于支付手续费、基础设施等固定/平台成本。
- 上游预算上限为 $8.40。
- 目标毛利率按收入口径为 10%。
- 模型折算系数必须保证在所有允许模型混合使用时仍满足成本上限。

### 3.3 工程目标

- 计费规则由受信任的 Main/Harness 侧拥有，Renderer 只展示结果。
- 计费配置版本化，价格变更可追溯、可回滚。
- 请求扣费具备幂等性，重试不能重复扣款。
- 会话日志不承载不可重建的 UI 余额状态；余额和用量以计费账本为准。

## 4. 非目标

- 本 RFC 不覆盖支付网关、退款、优惠券、税费和发票。
- 本 RFC 不支持图片生成、TTS、Embedding、OCR 或按次计费模型。
- 本 RFC 不为每个模型创建独立的现金余额。
- 本 RFC 不改变官方 API 费用的基础计算方式；输入和输出 token 仍可用于计算一次请求的官方基础费用，但不再建立输入余额和输出余额两个额度池。
- 本 RFC 不承诺用户可以把每个模型都单独消费满 $40；$40 是单模型上限，总余额 $60 是跨模型共享上限。

## 5. 术语

| 术语 | 定义 |
|---|---|
| 套餐额度 | 用户可见的共享余额，初始为 $60，单位为额度美元 |
| 官方基础费用 | 按官方 API 输入/输出价格和实际 token 用量计算出的单次费用 |
| 有效折扣率 | AIBerm 页面用于统一计算的单一折扣率 |
| 上游成本系数 | 1 - 有效折扣率，表示每 $1 官方基础费用对应的预算成本上限 |
| 套餐扣费系数 | 官方基础费用转换为套餐额度扣减的倍率 |
| 官方等值额度 | 用官方 API 价格计算的模型使用价值，用于展示单模型 $40 上限 |
| 单模型政策上限 | 每个模型最多 $40 官方等值费用，不是独立钱包 |
| 计费配置版本 | 一组在同一生效时间内使用的价格、折扣和系数配置 |

### 6.1 配置解释

- gpt-5.6-sol 与 gpt-5.6-terra 继续使用原 AIBerm 折扣对应的系数；Luna 因官方价格下调而单独使用 6.5714，避免按旧价格低估上游成本。
- Luna 的 $40 是单模型硬上限；由于它的系数较高，初始共享 $60 余额全部只使用 Luna 时，动态可用官方等值额度约为 $9.13。
- Claude Opus 5 和 Sonnet 5 的上游成本系数相同，因此套餐扣费系数相同。
- Claude Fable 5 的成本系数略高于 gpt-5.6-sol，因此同样的官方基础费用会多扣一些套餐额度。
- $40 单模型上限适用于上述全部 6 个模型，便于用户理解和运营控制。

## 7. 经济模型与公式

### 7.1 套餐预算

~~~text
用户收入                  = $10.00
目标利润（10% 收入口径）    = $1.00
支付/基础设施预留           = $0.60
可用上游成本预算             = $10.00 - $1.00 - $0.60 = $8.40
用户可见套餐额度             = $60.00
每 1 美元套餐额度允许的成本   = $8.40 / $60.00 = 14.00%
~~~

上述 $8.40 是包含上游价格波动余量的预算上限。若 AIBerm 实际账单低于按折扣率推导的上限，实际毛利会高于 10%；手续费、税费、退款等不在本 RFC 的 $0.60 预留之外自动吸收。

### 7.2 模型系数

~~~text
上游成本系数 = 1 - 有效折扣率
套餐扣费系数 = 上游成本系数 / 14.00%
~~~

例如 gpt-5.6-sol：

~~~text
有效折扣率    = 81.6%
上游成本系数  = 18.4%
套餐扣费系数  = 18.4% / 14.0% = 1.3143
~~~

例如 Claude Opus 5：

~~~text
有效折扣率    = 85.0%
上游成本系数  = 15.0%
套餐扣费系数  = 15.0% / 14.0% = 1.0714
~~~

### 7.3 请求扣费

~~~text
officialCostUsd          = Cocode Nut 现有官方 API 计价结果
quotaDebitUsd            = officialCostUsd × model.quotaMultiplier
upstreamCostCeilingUsd   = officialCostUsd × model.upstreamCostRatio
actualUpstreamCostUsd    ≤ upstreamCostCeilingUsd
~~~

账户账本只扣除 quotaDebitUsd：

~~~text
quotaBalanceUsd = quotaBalanceUsd - quotaDebitUsd
~~~

内部同时记录 officialCostUsd、upstreamCostCeilingUsd 和可取得的 actualUpstreamCostUsd，用于审计与利润分析。actualUpstreamCostUsd 以 AIBerm 实际账单为准；折算公式使用的是预算上限，不要求输入、输出分别建立额度池。

### 7.4 成本不超预算的证明

根据系数定义：

~~~text
actualUpstreamCostUsd
≤ upstreamCostCeilingUsd
= officialCostUsd × upstreamCostRatio
= quotaDebitUsd × 14.00%
~~~

因此，只要总套餐扣减不超过 $60：

~~~text
总实际上游成本 ≤ $60 × 14.00% = $8.40
~~~

这个结论对单模型和混合模型都成立，不需要预设用户的模型选择比例。

## 8. $40 单模型上限的定义

本 RFC 将“每个模型可用额度 $40”定义为：

~~~text
该模型累计官方等值费用 ≤ $40.00
~~~

它不是：

- 每个模型各自拥有 $40 独立余额；
- 用户可以把 6 个模型分别消费 $40；
- 不同模型都按 1:1 消耗套餐余额。

### 8.1 单模型上限消耗的套餐额度

| 模型 | $40 官方等值费用对应的套餐扣减 | 使用后剩余总余额（初始 $60、未混用） |
|---|---:|---:|
| gpt-5.6-sol / Terra | $52.57 | $7.43 |
| gpt-5.6-luna | $262.86* | 共享余额最多支持约 $9.13 官方等值额度 |
| Claude Fable 5 | $54.29 | $5.71 |
| Claude Opus 5 | $42.86 | $17.14 |
| Claude Sonnet 5 | $42.86 | $17.14 |

\* Luna 的 $262.86 是达到完整 $40 单模型上限所需的理论扣减；初始共享余额只有 $60，因此实际会先受共享余额限制。

### 8.2 动态可用额度

当前模型的可用官方等值额度应实时计算为：

~~~text
modelAvailableOfficialUsd =
MIN(
  modelCapUsd - modelUsedOfficialUsd,
  quotaBalanceUsd / model.quotaMultiplier
)
~~~

初始余额为 $60 时，6 个模型都显示 $40，因为每个模型的政策上限先于总余额成为限制。随着用户消耗共享余额，模型可用额度会自动下降。

## 9. 用户体验设计

### 9.1 套餐总览

主卡片只展示一个总余额：

~~~text
Cocode Nut 套餐额度
剩余：$60.00 / $60.00
~~~

同时展示一句说明：

> 不同模型按不同折算系数扣减；所有模型共享同一套餐额度。

### 9.2 模型选择器

每个允许模型展示：

- 模型名称
- 当前模型扣费系数，例如 1.3143×
- 单模型上限：$40.00 官方等值额度
- 当前预计可用官方等值额度，例如 $40.00

模型卡片不得把 $40 渲染成独立钱包余额，避免用户误以为 6 个模型各有 $40。

### 9.3 请求进行中与完成后

请求完成后显示：

~~~text
官方等值费用：$2.00
套餐额度扣减：$2.63
剩余套餐额度：$57.37
~~~

默认折叠详细信息；在账单明细中可展开查看：

- 模型
- 官方输入/输出 token 数
- 官方基础费用
- 模型折算系数
- 套餐扣减
- 计费配置版本

### 9.4 余额不足

当套餐余额不足以覆盖最小可计费单位时，拒绝请求并返回：

~~~text
套餐额度不足。当前模型预计还可使用 $X.XX 官方等值额度。
~~~

不得允许余额变为负数，也不得因为客户端重试造成重复扣款。

## 10. 权威数据与持久化

### 10.1 账户级账本

建议维护以下账户级字段：

~~~text

quotaGrantedUsd           // 60.00
quotaBalanceUsd           // 当前共享余额
quotaConsumedUsd          // quotaGrantedUsd - quotaBalanceUsd
modelCapUsd                // 40.00

periodEnd
status
~~~

### 10.2 模型用量统计

单模型政策上限需要统计用量，但不需要创建单独余额：

~~~text
modelId

~~~

officialUsageUsd 只用于 $40 单模型上限和展示；真正决定账户还能否继续调用的是 quotaBalanceUsd。

### 10.3 扣费流水

每次成功计费写入不可变流水：

~~~text

sessionId

officialCostUsd
upstreamCostCeilingUsd
actualUpstreamCostUsd
quotaMultiplier
quotaDebitUsd
balanceBeforeUsd

pricingVersion
createdAt
~~~

账本余额可以是聚合字段，但流水必须保留，便于对账和重建。

## 11. 请求处理流程

1. 受信任服务读取账户当前余额、模型用量和生效中的计费配置。
2. 校验模型是否在 allowlist 中。
3. 计算本次官方基础费用 officialCostUsd。
4. 计算模型套餐扣减 quotaDebitUsd。
5. 校验：
   - quotaBalanceUsd >= quotaDebitUsd
   - modelUsedOfficialUsd + officialCostUsd <= 40.00
6. 在同一事务中锁定账户账本并写入扣费流水。
7. 上游请求成功后确认扣费；如果系统采用预扣费，失败时写入冲正流水，不直接修改历史流水。
8. 向 GUI 推送新的余额快照和当前模型可用额度。

### 11.1 预扣费与失败请求

推荐采用“预估预扣 + 最终结算”：

- 请求开始时，按最大可能费用预扣，避免并发请求超卖。
- 请求完成后按实际官方费用结算差额。
- 上游失败、超时或被取消时，释放未使用预扣部分。
- 所有预扣、结算、释放都使用同一个 requestId 幂等。

如果当前上游 API 只能在响应后取得准确 token 用量，则至少需要账户级串行化或原子条件更新，不能先读余额、后无锁写余额。

## 12. 幂等性、并发与一致性

### 12.1 幂等键

客户端重试必须携带稳定的 requestId。服务端对 accountId + requestId 建唯一约束：

- 已成功扣费：返回原扣费结果。
- 已预扣未结算：继续处理原请求状态。
- 已失败并冲正：不得再次扣款。

### 12.2 原子扣减

余额扣减必须满足条件更新：

~~~sql
UPDATE quota_ledger
SET quota_balance_usd = quota_balance_usd - :debit
WHERE account_id = :account
  AND quota_balance_usd >= :debit;
~~~

实际实现可使用项目现有数据库抽象，但不能将扣费规则放在 Renderer。

### 12.3 多设备同步

余额快照和扣费流水以服务端为准。GUI 收到 quota.updated 事件后更新本地展示；本地缓存只用于乐观显示，不能作为扣费依据。

## 14. GUI 设计要求

### 14.1 额度状态组件

在全局导航或账户区域显示：

- 剩余套餐额度 $X / $60
- 当前计费周期
- 当前选中模型的预计官方等值可用额度

### 14.2 模型选择器状态

模型选择器必须区分：

- 可用：总余额和单模型上限都足够。
- 接近上限：单模型官方等值用量剩余低于 20%。
- 套餐余额不足：共享余额不足。
- 单模型上限已用完：该模型达到 $40，但其他模型仍可能可用。
- 已下线：模型不在当前计费配置 allowlist 中。

### 14.3 文案

推荐用户文案：

> 每月含 $60 Cocode Nut 套餐额度。不同模型按不同系数扣减，所有模型共享这一个额度；每个模型本月最多可使用 $40 官方等值用量。

避免使用：

- “每个模型都有 $40 余额”
- “所有模型都是 1:1 扣费”
- “输入额度/输出额度”

~~~

管理端的 upstream 成本预览使用固定的 1M 输入 + 1M 输出参考样本，在当前可用的
AIBerm active channel 中筛选完整且健康的 binding，并比较每条 binding 的输入价与输出价总和；
只选择总成本最低的一条。不会把不同 binding 的输入价和输出价拼接成不存在的价格。
真实请求仍按实际命中的 channel、binding 和价格档位结算，最便宜 binding 仅用于运营预算估算。

### 15.2 生效规则

- 新价格配置只对新请求生效。
- 已创建的预扣费沿用创建时的 pricingVersion。
- 旧版本保留到所有关联流水完成对账。
- 价格缺失、折扣缺失或系数异常时，默认暂停该模型，不自动用 1:1 规则上线生产。
- 配置更新必须先通过离线计算和回归测试，再发布到受信任服务。

### 15.3 安全阈值

建议在上线前校验：

~~~text
0 < upstreamCostRatio <= 1
quotaMultiplier > 0
modelCapUsd = 40
quotaGrantedUsd = 60
~~~

管理端还必须校验混合模型场景的成本比例：

~~~text
upstreamCostRatio / quotaMultiplier <= 14.00%
~~~

这里的 `upstreamCostRatio` 使用当前可用 AIBerm upstream 中，完整 binding 在
`1M 输入 + 1M 输出`参考样本上的最低成本与官方参考成本之比。若系数低于
`ceil(upstreamCostRatio / 14.00%)`，管理端禁止发布；这样即使用户在多个模型之间混用，
共享 `$60` 额度对应的上游预算仍不超过 `$8.40`。单模型 `$40` 上限的成本展示仍作为
运营预览，但不能替代这个比例校验。

`quotaMultiplierPPM` 和 `upstreamCostRatioPPM` 使用整数 ppm 存储（1,000,000 = 1.000000×），保留至少六位小数精度；表格和 GUI 只展示四位小数。禁止使用展示后的 `1.0714` 反向计算真实扣费，以免长期累积舍入误差。

如 AIBerm 价格突然上调，服务端应拒绝旧配置继续扩大额度，避免因缓存或手工配置造成超支。

### 15.4 仓库落点与职责边界

- **Harness/Host 受信任服务**：持有 AIBerm 凭据、官方费用计算、系数配置、账户账本、幂等扣费和实际成本对账；Renderer 不得参与最终扣费。
- **`cocode-gui/packages/cocode/cocode-models`**：维护 6 个模型的展示元数据、allowlist 和只读额度字段映射，不保存账户余额。
- **`cocode-gui/packages/connection`**：承载额度查询、扣费结果和 `quota.*` 事件的 wire contract；只做传输和协议校验。
- **Main/Preload**：转发受信任服务返回的额度快照和扣费结果，不重新计算模型系数。
- **Renderer/UI**：展示统一 $60 余额、当前模型 $40 官方等值上限和解释文案；本地缓存只用于暂态显示。
- **TUI**：复用同一额度查询和扣费语义，不实现第二套价格表或余额规则。

任何客户端传入的模型 ID、扣费系数或余额字段都视为不可信输入；服务端必须以 `pricingVersion` 和 allowlist 中的配置为准。

## 16. 观察性与对账

至少记录以下指标：

- quota.debit.usd
- quota.upstream_cost_ceiling.usd
- quota.actual_upstream_cost.usd
- quota.official_cost.usd
- quota.margin.usd
- quota.margin_rate
- quota.balance_exhausted.count
- quota.model_cap_reached.count
- quota.debit.reversal.count
- quota.pricing_version.mismatch.count

每日对账应验证：

~~~text
Σ quotaDebitUsd
≈ quotaGrantedUsd - quotaBalanceUsd
Σ actualUpstreamCostUsd
≤ Σ quotaDebitUsd × 14.00%
~~~

由于上游价格、汇率、手续费和四舍五入可能产生微小差异，内部金额建议使用整数微美元或至少 6 位小数存储，展示时再保留 2 位小数。

## 17. 迁移与发布计划

### 阶段 0：离线验证

- 固化 6 个模型 allowlist。
- 导入 aiberm-2026-08-27-v1 计费配置。
- 用历史请求样本回放混合模型场景。
- 验证所有账户在额度用尽前不会产生负余额。

### 阶段 1：影子计费

- 继续使用现有扣费结果。
- 同时计算新 quotaDebitUsd 和 upstreamCostCeilingUsd，但不影响用户余额。
- 对比现有官方费用、AIBerm 账单和新模型系数。

### 阶段 2：灰度

- 对内部账户启用 $60 总额度和 $40 单模型上限。
- 观察 7 天混合使用、重试、超时、取消和多设备并发。
- 灰度期间保留旧计费配置的回滚开关。

### 阶段 3：正式上线

- 新套餐账户使用新账本。
- 旧账户按迁移策略补发或折算余额，不直接覆盖历史流水。
- 完成客服、产品页、帮助文档和账单明细文案同步。

## 18. 测试计划

### 18.1 公式测试

- gpt-5.6-sol / Terra：系数应为约 1.3143；Luna：系数应为 6.571429。
- Claude Fable 5：系数应为约 1.3571。
- Claude Opus/Sonnet 5：系数应为约 1.0714。
- 初始 $60 下每个模型可用官方等值额度均为 $40。
- 余额 $20 时：
  - gpt-5.6-sol 可用额度约 MIN(40, 20 / 1.3143) = $15.22。
  - Claude Opus 5 可用额度约 MIN(40, 20 / 1.0714) = $18.67。

### 18.2 账本测试

- 并发请求不能超扣。
- 同一 requestId 重试不能重复扣费。
- 上游失败能够完整释放预扣。
- 结算差额不会造成余额负数。
- 单模型达到 $40 后，该模型拒绝，其他模型仍可继续使用共享余额。

### 18.3 UI 测试

- 账户只显示一个 $60 总余额。
- 6 个模型初始均显示 $40 单模型上限，但不显示为 6 个独立钱包。
- 切换模型后，预计可用额度正确刷新。
- 总余额不足和单模型上限用尽显示不同状态。
- 断线重连后以服务端快照覆盖本地缓存。

### 18.4 回放测试

使用包含以下情况的真实脱敏样本回放：

- 只使用 gpt-5.6-sol。
- 只使用 Claude Opus 5。
- gpt-5.6-sol 与 Claude Opus 5 混用。
- 先使用高折扣模型，再使用低折扣模型。
- 请求超时后客户端重试。
- 两台设备同时请求。

验收条件：任何回放路径都满足总上游成本不超过 $8.40 的预算模型，且账本可从流水重建。

## 19. 备选方案与拒绝理由

### 方案 A：每个模型单独发 $40 余额

拒绝原因：会形成 6 个独立承诺，用户可以把理论额度叠加到 $240，而产品只有 $10 收入。

### 方案 B：所有模型都按官方价格 1:1 扣 $60

拒绝原因：无法反映 AIBerm 折扣差异；低折扣模型可能消耗掉大部分上游预算。

### 方案 C：输入、输出分别建立额度池

拒绝原因：产品需要的是一个总额度，且用户不应理解或管理两个余额；实际 token 维度可以保留在官方基础费用明细中，但不应形成两个用户额度池。

### 方案 D：只设置隐藏的上游成本预算，用户仍按官方价 1:1 扣费

拒绝原因：可以控制成本，但可能出现用户仍看到余额，却因为隐藏预算耗尽而无法调用，体验和解释成本较高。

## 20. 已确定的运营策略

1. $40 单模型上限按当前订阅/额度周期重置，与共享套餐余额同时刷新。
2. 失败且未确认产生上游用量的请求释放预扣；已经确认的上游用量进入实际结算并计入官方等值用量。
3. 用户明细同时展示官方等值费用、模型系数、套餐扣减和剩余共享余额；输入/输出 token 仅作为费用明细，不形成两个额度池。
4. 价格版本在预留时冻结；后续结算沿用该版本，新的请求使用当时生效的最新版本。
5. 当前 $10 套餐固定保留 $0.60，允许的上游成本预算为 $8.40；未来若套餐价格变化，按同一公式重新发布配置版本。
6. 高成本模型继续使用现有单请求、RPM、TPM 和并发限制；不额外引入第二套额度规则。

## 21. 验收标准

本 RFC 只有在以下条件全部满足后才能标记为 Implemented：

- 用户新周期初始看到 $60.00 一个总额度。
- 允许模型只有 6 个指定模型。
- 每个模型的官方等值用量上限为 $40.00。
- 所有模型共享同一个 quotaBalanceUsd。
- 请求扣费使用正确的模型折算系数。
- 混合模型使用不会导致上游成本模型超过 $8.40。
- 账本扣费幂等，余额不会出现负数。
- GUI、Main、Preload、Contracts、Harness/Host 的边界职责清晰。
- 计费配置带版本和生效时间，流水可以追溯到具体版本。
- 断线、重试、多设备并发、上游失败和预扣释放均有自动化测试。
- 用户文案明确说明 $60 是共享套餐额度，$40 是单模型官方等值上限，不是 6 个独立余额。

## 22. 结论

采用“共享 $60 总额度 + 每模型折算系数 + 每模型 $40 官方等值上限”的方案。

该方案同时满足：

- 用户看到的套餐承诺仍然是 $60；
- 不同模型根据 AIBerm 折扣消耗速度不同；
- 6 个模型不会产生 6 份独立余额；
- 用户可以混用模型；
- 运营可以限制单个模型最多 $40 官方等值使用量；
- 在配置正确的前提下，上游成本上限和利润目标可由数学关系直接保证。
